# Preflight obligatorio al comenzar cada fase

Aplicar antes de la primera selección operativa, asignación, activación o modificación de **cada fase**, incluidas las de planificación, verificación, entrega y publicación. Repetir al reanudar una fase, recibir un relevo o cambiar una condición relevante. El preflight del plan o de la fase anterior no habilita la siguiente. El agente activo responde de este control tanto en CODEX como en WORK o CHAT.

## Alcance y orden

1. Recuperar en lectura el plan literal vigente, su versión, la fase, dependencias, candidata/base, alcance y criterios de aceptación y entrega. Conservar sus IDs y orden. Una fase de solo planificación se evalúa hasta entregar el plan solicitado; una de implementación se evalúa hasta el cierre que exige su contrato.
2. Inventariar las capacidades realmente expuestas en esta sesión y obtener evidencia actual mediante inspecciones de solo lectura y consultas sin efectos. Leer herramientas, fuentes o metadatos para comprobar viabilidad es parte del preflight. Todavía no fijar recursos operativos, asignar agentes/trabajos, cambiar selección de memoria, instalar, activar, desplegar ni escribir en el destino. No probar un permiso mediante una escritura real; combinar autorización vigente, operación expuesta y evidencia actual de ACL, elegibilidad o contrato de la herramienta/destino. Usar consultas de permisos o validación sin efectos cuando existan. Si no hay dry-run seguro, no ejecutar la operación para probarla; precisar qué viabilidad acredita la inspección y qué resultado solo podrá observarse durante el trabajo. Si falta evidencia decisiva, declarar la incertidumbre.
3. Evaluar el recorrido completo **ejecutar → verificar → entregar**, con todas las operaciones imprescindibles hasta satisfacer el gate de esa fase. Poder editar sin poder ejecutar sus pruebas, acceder al verificador requerido o entregar/publicar lo contratado no permite `GO`. Un build o el nombre de una herramienta no acredita la capacidad restante. No exigir pruebas de resultado antes de implementar: aquí se comprueba que será posible ejecutarlas y observarlas.
4. Antes de cualquier selección operativa o cambio, comunicar el dictamen, sus límites y cualquier transición o intervención necesaria. Con `GO`, continuar autónomamente dentro de la autorización vigente; no pedir una segunda confirmación. Con otro resultado, resolver primero la condición indicada, salvo la preparación revisable expresamente delimitada para una aceptación futura en la sección siguiente. Las demás actividades se limitan a inspecciones o preparativos independientes. No recortar ni dividir silenciosamente la fase para convertir un cierre imposible en `GO`.

## Comprobaciones mínimas

| Área | Evidencia que debe recuperarse para esta fase |
|---|---|
| Herramientas | Operaciones reales expuestas, firmas, restricciones y compatibilidad. Una habilidad, ruta o nombre de agente no instala una capacidad. |
| Accesos | Identidad del proyecto/destino, cuenta/sesión y alcance efectivo de lectura, escritura, ejecución y consulta de resultados necesarios; diferenciar acceso de autorización. No registrar secretos. |
| Autorización | Petición o permiso vigente que cubre cada efecto que se ejecutará ahora, límites, revocación y STOP. Separar los efectos ya autorizados de cualquier aprobación futura pendiente; no declarar esa aprobación como concedida. Reutilizar la autorización ya concedida; si falta un permiso esencial, explicitar el efecto concreto. Un cambio de host no evita una denegación. |
| Ejecución | Runtime, dependencias, recursos y canales suficientes para ejecutar la fase completa; comprobar el destino mediante [target-preflight](../../bago5/references/target-preflight.md) cuando la operación dependa de una versión, runtime o configuración externa. |
| Verificación | Pruebas y evidencias exigidas, herramientas para ejecutarlas y leer sus resultados, independencia real cuando el gate la requiera y posibilidad de comprobar la candidata exacta. |
| Entrega | Canal y permisos para guardar, integrar, publicar o entregar lo contratado y verificar el resultado. Publicar solo es necesario si forma parte de esta fase. |
| Dependencias | Gates previos satisfechos, entradas vigentes, esquema realmente admitido, conflictos y concurrencia. Recuperar memoria no reanuda un STOP ni crea autorización. |

Declarar también de forma explícita si hace falta otro entorno y si hay intervenciones humanas pendientes, aunque ocurran al final. Registrar la operación, el momento, el motivo y el resultado que se deberá observar. Clasificarla como `BEFORE_START` si es necesaria antes de preparar trabajo dependiente, o `BEFORE_COMPLETION` si requiere una candidata revisable y se resolverá antes del efecto final o cierre. «El usuario está disponible» no completa autenticación, confirmación, presencia, MFA, prueba manual o aceptación aún pendiente. Si la aceptación humana es parte del cierre de la fase, se anuncia desde el inicio; una fase cuyo contrato solo exige preparar algo revisable puede cerrar al entregarlo, conservando la aceptación como pendiente fuera de ese alcance.

## Dictamen y continuidad

| Dictamen | Condición y conducta |
|---|---|
| `GO` | Evidencia actual suficiente para todo el alcance, autorización vigente, sin STOP, transición ni intervención pendiente. Ejecutar, comprobar y entregar sin una confirmación redundante. |
| `CAMBIO_ENTORNO` | El entorno actual no permite completar la fase y existe un destino propuesto pertinente. Indicar `CODEX → WORK`, `WORK → CODEX` u otra transición concreta, qué capacidad falta, qué se espera del destino y el punto de retorno. Preparar el relevo; el destino repite el preflight con sus propias herramientas, accesos y permisos antes de actuar. |
| `REQUIERE_USUARIO` | Falta una acción/presencia/permisión humana imprescindible, ahora o en el cierre. Indicar quién, qué, cuándo, por qué y qué evidencia permitirá reanudar. Preparar una candidata únicamente bajo la excepción `can_prepare` descrita abajo; no ejecutar el efecto sometido a aprobación. Si también cambia el entorno, mostrar ambas condiciones. Tras la intervención, verificar su resultado y repetir el preflight, sin volver a pedir permisos que sigan vigentes. |
| `BLOQUEADO` | STOP, denegación, incompatibilidad conocida, dependencia incumplida o entrada inválida. Explicar la causa y la condición concreta de desbloqueo; no eludirla cambiando de herramienta o de entorno. |
| `NO_COMPROBADO` | Falta evidencia decisiva, es obsoleta, contradictoria o pertenece a otro contexto. Completar inspecciones permitidas; no convertir ausencia de prueba en capacidad disponible. |

STOP y una autorización denegada dominan los demás resultados. Un cambio de entorno no implica que el destino esté comprobado ni transfiere credenciales o permisos. El relevo contiene objetivo, plan/versión, fase y trabajo exactos, fuentes/candidata, alcance, autorización y STOP vigentes, resultado del preflight, carencias, intervención humana, evidencias y siguiente operación. No inventar un relevo hacia la propia sesión si puede completar el contrato actual.

## Preparar la candidata para una aceptación futura

No convertir «crear candidata → mostrarla → aceptación humana final» en un bloqueo circular. Si todas las intervenciones pendientes son `BEFORE_COMPLETION`, el agente puede preparar el resultado revisable que ya está autorizado **después de anunciar desde el inicio** el punto de control y lo que requerirá al usuario. No exigir que confirme ahora su disponibilidad ni pedir otra vez un permiso vigente. Una autenticación, permiso esencial o presencia necesarios para preparar son `BEFORE_START` y no admiten esta excepción.

Registrar de forma explícita el alcance opcional `preparation`: `steps` (pasos concretos permitidos), `authorization_ref` y `authorization_source_type` (instrucción o aprobación vigente ya comprobada), `notice_ref` (aviso emitido antes de trabajar) y `context_key` actual. La referencia de autorización debe coincidir con una observación de autorización `PASS`; no basta que exista un campo escrito por el agente. Cada paso debe ser necesario para producir, probar o mostrar la candidata revisable y estar cubierto por esa autorización. La acción sujeta al gate, como publicar, migrar o aceptar, queda excluida de los pasos permitidos mientras siga pendiente.

Rechazar recibos que incluyan la misma acción pendiente entre los pasos permitidos. El comprobador detecta coincidencias textuales normalizadas; corresponde al agente detectar también equivalencias de significado, contrastar el alcance real y no renombrar una acción para eludir su gate.

El comprobador devuelve `REQUIERE_USUARIO`, `can_start: false`, y solo devuelve `can_prepare: true` con los `preparation_steps` delimitados cuando todas las condiciones estén comprobadas: pendientes exclusivamente `BEFORE_COMPLETION`, aviso y autorización aplicables, cobertura fresca de las siete áreas, sin fallos ni incertidumbre, STOP, denegación, transición de entorno o preflight de destino pendiente. Si falta una condición, `can_prepare: false`. En ningún caso ejecuta esos pasos ni convierte la aceptación pendiente en concedida.

Ejecutar únicamente los pasos permitidos y detenerse en el punto anunciado para mostrar la candidata y solicitar la intervención concreta. Mantener la fase abierta y conservar todos sus criterios, sin recortarla, simular un cierre ni marcar `GO`. Tras la acción humana, comprobar su resultado y repetir el preflight antes del efecto final. Esta excepción habilita preparación acotada; `can_start` sigue representando la viabilidad declarada del recorrido autónomo completo de la fase.

## Vigencia, registro y comprobador

Vincular el preflight al proyecto, objetivo, plan/versión, fase/revisión, sesión, host, entorno, candidata/base, alcance, aceptación y **un intento nuevo al iniciar o reanudar**. Invalidarlo si cambia cualquiera de ellos, herramientas, acceso, permisos, dependencia, selección, STOP o disponibilidad del verificador. El contexto actual debe comprobarse por separado, no copiarse del recibo que se quiere validar. Al cambiar la candidata mediante una edición prevista, vincular la verificación a la nueva candidata y revalidar las condiciones afectadas; reutilizar evidencia no afectada solo tras confirmar su vigencia. No pedir otra autorización para el mismo alcance ya autorizado. Ante error de acceso o capacidad durante la ejecución, detener las nuevas acciones dependientes, conservar evidencia y reevaluar. Un fallo de prueba no invalida por sí solo la capacidad de depurar: corregir dentro del alcance autorizado si herramientas y permisos siguen disponibles, y repetir las pruebas pertinentes. Una comprobación inicial no garantiza que el entorno permanezca disponible ni que las pruebas futuras pasarán.

Comunicar al principio, con el detalle proporcional a la fase: `Fase <id> · preflight <dictamen> · entorno <host> · ejecutar/verificar/entregar <estado> · transición/intervención <ninguna o acción concreta>`. Añadir las referencias decisivas cuando haya límites o impedimentos. Este anuncio no convierte una fase en ejecutada o aceptada.

Usar el registro ya autorizado del plan o la conversación; persistir únicamente si hay autorización y campos admitidos. No crear archivos, cambiar memoria ni añadir campos al backend solo para cumplir este control. El [schema de recibo v1](../schemas/phase-preflight.schema.json) es un contrato local de comprobación, no una migración del modelo v1/v2 ni prueba de soporte del backend.

El [comprobador](../scripts/phase_preflight.py) clasifica recibos con Python y `jsonschema` cuando estén disponibles. Invocación: `python phase_preflight.py recibo.json --context contexto-actual.json`. Exige contexto actual aparte, cobertura de las siete áreas, referencias, fechas vigentes, coherencia y ausencia de intervenciones/transiciones pendientes para `GO`. Cada observación lleva `source_type`, `source_ref` y el `context_key` de ese contexto; el hash solo vincula datos y no prueba funcionamiento. Para autorización admitir únicamente `USER_INSTRUCTION` o `EXPLICIT_APPROVAL`, y comprobar que cubren las acciones concretas. Para las demás áreas admitir `HOST_TOOL`, `AUTHENTICATED_ACCESS`, `SOURCE_READ` o `TARGET_PROBE` según la comprobación real. Memoria, chats históricos, resúmenes o una declaración de capacidad sin fuente actual no acreditan acceso ni autorización. Estos tipos declarados no autentican la fuente: contrastarla siempre. Una intervención completada conserva `completed_at` como fecha del hecho y `captured_at` como comprobación actual de su efecto, con `evidence_ref` y `context_key`; una autorización que continúa vigente no se solicita de nuevo por ser anterior al recibo. Cada elemento de `required_target_actions` identifica `action_id`, `target_id` y `environment`; reutilizar el comprobador de destino y cotejar esos tres valores, sin aceptar el recibo coherente de otro destino. El procedimiento observa y contrasta las fuentes; el script solo comprueba la coherencia de lo declarado. No crea evidencias, prueba accesos, ejecuta trabajo, concede permisos ni intercepta herramientas del host; el agente sigue obligado a comprobar las fuentes y aplicar el resultado. Si falta el ejecutor o la dependencia, aplicar el mismo contrato en la conversación y declarar que el comprobador automático no se ejecutó, sin instalar nada por defecto.
